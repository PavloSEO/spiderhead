- Grouped findings now report how many pages they cover: every finding summary in
  `scan-findings-page` (CLI and MCP `seo_scan_findings_page`) and in the observer's scan-evidence
  summaries carries `affected_urls` — the member count of the finding's group — next to the
  existing counts (#1411). A check emitted through `add_site_wide` (for example `LOW_TEXT_RATIO`,
  `HEADING_IN_PAGE_CHROME`, `H2_DUPLICATE`, `DUPLICATE_INTERNAL_LINK`) is one finding row plus a
  group of member URLs, so the page reported `matched: 1` with no signal that the defect touched
  hundreds of pages: on a retained native scan of spiderhead.dev (468 URLs) `LOW_TEXT_RATIO` was
  one finding with a group of 349 member URLs. The group size is read in SQL from the audit.v2
  companion (both storage revisions) or from the legacy audit slot; existing output fields are
  unchanged.
- A by-URL findings lookup now returns grouped findings whose members include the URL, marked
  `via_group: true`, instead of only rows whose own `target_url` matches (#1411). Previously the
  `LOW_TEXT_RATIO` finding above was invisible for every member page — a lookup for
  `https://spiderhead.dev/features` returned 6 other findings and looked clean — because only the
  one row carrying the finding answered. Membership now decides: each member URL sees the grouped
  finding, a URL outside the group does not, and the unfiltered page is unchanged (`via_group`
  appears only on lookups that matched through a group). The same rule and marker apply in the
  audit.v2 companion at storage revisions 2 and 3 and in the bounded legacy audit slot.
