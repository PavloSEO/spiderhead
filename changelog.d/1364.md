- `robots-check` treated every 4xx answer except 429 as "no robots.txt (crawl allowed)" (`seohead/checks/robots.py`). On a host whose bot protection answers 401/403 for robots.txt, that reported `exists: false` — a claim that the file does not exist, built from a response that actually says the *client* was refused; the file may well exist behind the WAF. 401/403 now return a distinct result: `exists: null`, `state: "access_denied"`, with a note that the rules could not be read and the response may be a WAF block, and no `path_checks` are invented from rules that were never served (#1364). 404 and 410 keep the RFC 9309 "absent, crawl allowed" reading.
- `ai-bots-check` no longer reports AI bots as "allowed by default" when robots.txt answers 401/403. The handler applied the genuine-404 "no restrictions" branch to every 4xx below 500 (observed live: a WAF-protected host showed all 18 bots "allowed by default"). A denied robots.txt now returns `ok: false` with the status code and an error saying access was denied and the response may be a WAF block — the same shape as the existing 5xx branch — so neither the standalone tool nor site-audit's `ai_bots_check` step can quote a permission the server never stated.
