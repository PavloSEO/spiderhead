- The HTTP client could be refused by bot protection on every request (observed live: a Cloudflare-fronted Shopify storefront answered 403 to the toolkit's Python client and 200 to plain curl at the same pace), and every tool then audited the block page — "missing HSTS/CSP", "no analytics" and a very high TTFB that all described the challenge body, not the site. A 403/429 carrying WAF markers is now classified as such by `waf_block_reason` in `seohead/recon/net.py`: the `cf-mitigated` header (`challenge`, `block`, `managed`), a Cloudflare edge `server` header, or a known challenge-body marker (`cdn-cgi/challenge-platform`, `cf_chl_`, "Just a moment...", and friends) read from the first 8 KB. A plain origin 403 without markers stays a regular error, and a 2xx is never a block (#1363).
- `parser.fetch_html`/`parse_url` carry the classification on the fetch result as `blocked_by_waf` with the short reason (a new optional `ParseFetched` field in `seohead/core/models.py`), so callers can report the block instead of the body. Detection and honest reporting only: nothing here spoofs a User-Agent, routes through proxies, or solves challenges — the operator's paths around a block are an allowlist for the crawler or a supplied export. Inspecting an error page on purpose keeps working through the single-URL tools with supplied HTML.
