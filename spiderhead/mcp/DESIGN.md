# Design notes: `spiderhead-mcp`

Scope: the MCP surface only — catalog, profiles, stdio JSON-RPC transport, protocol
dispatch, handler registry. Domain logic stays in other crates and plugs in via
[`handler::Registry`](src/handler.rs).

## Transport: own thin JSON-RPC layer (rmcp rejected after a spike)

The plan called for a spike of `rmcp` (official Rust MCP SDK) with a fallback to a
hand-written layer. The spike (rmcp **3.8.0**, minimal data-driven `ServerHandler`,
empirically diffed against the captured fixtures) showed rmcp imposes shapes the
reference baseline never emits:

1. **`initialize` capabilities diverge structurally.** rmcp answers
   `{"prompts": {},"resources": {},"tools": {}}` by default — no `experimental: {}`,
   no `listChanged: false` / `subscribe: false` members the oracle sends. The
   parity gate is 0 structural divergences, so every extra or missing key fails.
2. **Unknown methods error differently, and not overridably.** The oracle answers
   `-32602 "Invalid request parameters" data: ""`; rmcp answers `-32601` with the
   method name as the message — generated inside the framework's dispatch macro,
   not reachable from a handler.
3. **Version negotiation is stricter.** rmcp rejects versions outside its list
   with `-32022`; the oracle echoes any of its four supported versions verbatim.
4. rmcp 3.8 models the 2026-07-28 protocol generation (discover, inline lifecycle,
   per-request metadata, SEP-2322 `resultType`, task-based `CallToolResponse`
   enum). Matching an `mcp` SDK 1.30.0 server would mean auditing and fighting
   every version-conditional default on every response.
5. Cost: ~80 extra dependency packages and fast API churn (three type renames hit
   during the one-hour spike) versus zero new crates — everything the hand-written
   layer needs (`serde`, `serde_json`, `thiserror`) is already in the workspace.

One deviation from the task text: **no tokio**. The prescribed `ToolHandler::call`
is synchronous and the wire is line-sequential (`std::io` only); tokio would be an
unused runtime. Domain crates that need async work can thread it through their
handler internals — the `CallContext` progress queue stays the same.

## Catalog as data

`data/tools.json` is generated by the reference suite from the reference baseline
(five profile sessions plus registry introspection) and embedded with
`include_str!`. Tool specs are stored and served **verbatim** — including key
order, which `serde_json` preserves (`preserve_order` feature, already
workspace-wide) — so `tools/list` is byte-comparable to the oracle. The order of
the full profile is the live reference order, where the eleven progress-wrapped
tools sit at the end (the reference server re-registers them at startup).

## Wire-contract decisions (all verified against the oracle)

- **Check order in `tools/call`:** name/type envelope (`-32602` for non-object
  `arguments` too — the SDK's `CallToolRequestParams.arguments` is a dict) →
  catalog lookup for the *profile* → input-schema validation → handler. The
  reference server physically removes non-profile tools at startup, so any name
  outside the profile — even a globally known one — answers
  `Unknown tool: <name>` as an `isError` **result**, not a profile-gate error
  and not a JSON-RPC error.
- **Validation** reproduces the pydantic 2.13 diagnostics byte-identically
  (`validation.rs`): `<n> validation error(s) for <Tool>Arguments` blocks with
  `loc`/`type`/`input_value`/`input_type`, enum and union branch labels
  (`facets.list[str]`), `reference repr` of inputs, and pydantic's scalar
  coercions applied to accepted values (`"5"` → `5`, `"yes"` → `true`,
  integral floats, `bool`→`int`). `tools/list` stays wire-exact, so handler
  kwargs beyond the published schemas live in the catalog's
  `input_extensions` table and take part in call-time validation only.
- **Successful calls** mirror the oracle: `content[0]` is the pretty-printed JSON
  text, the value is duplicated as `structuredContent`, no `isError` key.
- **Version string:** the oracle reports the reference *mcp SDK* version; this
  server emits the same constant (`1.30.0`). Fixtures normalise it to `{VERSION}`
  (`gen/NORMALISATION.md`); parity tests substitute it back.
- **Progress:** queued through a channel during the handler call and written
  before the response — same order the oracle produces. Without a client
  `progressToken` it is silent (as in the reference reporter). The reference
  reporter's 0.5 s throttle and monotonicity guard belong to long-running domain
  handlers; they are not part of this crate's surface.
- **Bad input lines:** the oracle emits a `notifications/message` error
  notification (`logger: mcp.server.exception_handler`) and keeps serving — there
  is no id to answer. This server reproduces that exactly, key order included.
- **Cancellation:** calls are synchronous, so `notifications/cancelled` always
  arrives after completion; it is absorbed like the oracle absorbing unknown ids.
- **`ping`, `prompts/list`, `resources/list`** answer exactly what the oracle
  answers (empty objects / empty lists — the capabilities advertise them).

## What is deliberately not here

- HTTP transport, `mcp_control` state files, client registration — CLI/control
  domain, another slice. The binary takes `--profile` directly.
- Tool bodies: every call answers `NotYetPorted` until domain crates register.
- The reference the reference suite doc generator — build-time docs tooling.
